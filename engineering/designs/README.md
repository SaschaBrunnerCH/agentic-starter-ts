# Design notes

- [Blueprint graphics example](blueprint-graphics-example.md): the replaceable globe/map screen, native API boundaries and rendering evidence.

One file per proposed solution before a decision, named after the question. A design note states the requirements, goal and constraints, proposed behavior and interfaces, options with their evidence and tradeoffs, a recommendation, unresolved choices and a validation plan.

Link supporting [research records](../research/README.md) and retain enough context to understand the proposal without opening an issue or pull request. Research may conclude without a design note or selected solution. Keep one canonical explanation of each finding; the design note owns the evolving proposal.

The owner's answers are added to the note. Consequential decisions the project makes that constrain later work then become an [ADR](../adr/README.md), linked from the note. Maintain inherited tooling rationale in its engineering guide or code comments under [knowledge ownership and portability review](../agents/decision-workflow.md#knowledge-ownership). Notes kept outside the repository are not a source of truth.
